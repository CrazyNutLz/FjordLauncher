## 2. 推荐决策

采用“显式绑定实例 + 目标状态清单 + 启动前更新任务”。保留旧方案按需新增、替换、删除文件的用途；改进路径、校验、匹配和安装方式。

1. 路径相对于 `MinecraftInstance::gameRoot()`，例如 `config/OpenBlocks.cfg`。该方法兼容实例内 `minecraft` 与 `.minecraft` 目录，不能拼接启动器工作目录，也不能再附加 `.minecraft`。
2. 仅更新本地明确启用本服更新的实例，接口地址使用启动器的集中配置；不在 API 中重复填写包标识或渠道。完整客户端发布时写入本地启用设置；既有实例通过一次“绑定本服客户端”操作迁移，不通过名称模糊匹配，也不自动更新所有实例。
3. 开机后台可以查询清单并显示状态；实际应用放到点击启动后的任务链内。增加“检查客户端更新/修复”手动入口，调用同一个任务。
4. SHA-256 必填；先全部下载到暂存区并验证，再备份、安装、处理旧文件，最后提交状态。
5. 维护清单中的文件和 ZIP 展开目标，允许用明确配置的名称规则清理其他文件；不做无规则的目录同步清空。
6. 本次范围包括单文件、按名称删除和 ZIP 更新，统一使用备份与恢复机制。

## 3. 新 API 格式

只实现本节的新协议，不兼容旧规则，也不提供旧字段自动转换。仍不设置 size、channel、packId 或版本号。下面把所有支持的字段全部写出；可选字段可以省略，默认值见表格。

这是字段用法展示，不是可直接发布的清单：ZIP 地址和标注“替换”的哈希需要换成真实值；OpenBlocks 的哈希来自前面的实际验证。

```json
{
  "silent": true,
  "notice": "修复配置，清理旧模组并更新资源文件",
  "files": [
    {
      "path": "config/OpenBlocks.cfg",
      "sha256": "41348af14ece98c7d8113c34f6c9a61ba87fa384efddf12e3faccc7624f9e92b",
      "url": "https://resource.34learning.cn/tmp/OpenBlocks.cfg",
      "policy": "managed"
    }
  ],
  "remove": [
    {
      "dir": "mods",
      "match": "exact",
      "name": "ExampleMod-old.jar",
      "recursive": false,
      "sha256": "替换为旧文件真实的64位SHA256；不限制哈希时删除此字段"
    },
    {
      "dir": "mods",
      "match": "contains",
      "name": "OldExampleMod",
      "recursive": false
    }
  ],
  "archives": [
    {
      "path": ".",
      "sha256": "替换为ZIP文件真实的64位SHA256",
      "url": "https://example.com/client-resources.zip",
      "source": "client/",
      "policy": "managed"
    }
  ]
}
```

### 3.1 顶层字段

| 字段 | 必填 / 默认值 | 说明 |
| --- | --- | --- |
| `silent` | 可选，`true` | 整批静默更新；必须使用 JSON 布尔值。true 不弹确认和完成提示，false 在应用前展示说明与操作摘要并确认 |
| `notice` | 可选，空文本 | 整批更新说明，以纯文本显示 |
| `files` | 可选，`[]` | 单文件新增或替换列表 |
| `remove` | 可选，`[]` | 文件删除规则列表 |
| `archives` | 可选，`[]` | ZIP 解压更新列表 |

至少显式提供一个操作数组；空数组合法，表示当前没有相应操作。不能把缺少全部操作字段的任意 JSON 当成“无更新”。

`silent` 对 files、remove、archives 整批生效，不增加逐文件开关。它只控制交互方式，不改变下载校验、备份、恢复和启动前等待规则。

- `silent=true`：发现变更后自动下载和应用，不弹更新确认、notice 或成功对话框；主窗口状态/现有任务进度仍可显示“正在更新客户端”。notice 保存在更新详情中，供主动查看。
- `silent=false`：实际有变更时，一次展示 notice、待安装文件和删除摘要；确认后执行，取消则不修改文件并取消本次游戏启动。未知 ZIP 内容需要先下载到缓存建立索引，确认前不修改游戏文件。
- 无差异时不弹窗。成功清单摘要只用于避免重复主动展示 notice；silent=false 时只要有实际修改，仍需确认，不能用已读记录绕过确认。
- 静默失败不能无声放行：下载或校验失败、文件占用、恢复失败时，显示简短错误与重试入口；启动前任务失败则终止本次启动。正常更新过程不打断用户，失败反馈集中为一次，不逐文件弹窗。
- 手动点击“检查客户端更新/修复”时，即使 silent=true 也显示检查结果和进度，因为这是用户主动发起的操作；不额外要求更新确认。
- 静默不表示游戏运行时改文件，也不表示隐藏所有进度。开机后台仍只检查；自动应用由启动前任务触发，或由手动入口触发。

### 3.2 单文件 `files[]`

| 字段 | 必填 / 默认值 | 说明 |
| --- | --- | --- |
| `path` | 必填 | 相对实例游戏目录的文件路径，如 `config/OpenBlocks.cfg` |
| `sha256` | 必填 | 下载文件的 64 位十六进制 SHA-256，不能为空 |
| `url` | 必填 | HTTPS 下载地址 |
| `policy` | 可选，`managed` | `managed`：缺失或哈希不同则安装，覆盖前备份；`seed`：仅缺失时安装，保留已有文件 |

不填写大小：SHA-256 用于完整性验证。进度使用响应长度，长度未知时显示已下载字节和完成文件数。服务端清单就是目标状态，发布旧文件哈希也会同步回旧内容，不提供版本防降级。

### 3.3 删除规则 `remove[]`

| 字段 | 必填 / 默认值 | 说明 |
| --- | --- | --- |
| `dir` | 必填 | 搜索目录，相对游戏目录，例如 `mods`、`config/example` |
| `match` | 必填 | `exact`：完整文件名相同；`contains`：文件名包含指定字符串 |
| `name` | 必填 | 匹配文本，不能为空、纯空白或包含路径分隔符；对文件名含扩展名匹配，不对完整路径匹配 |
| `recursive` | 可选，`false` | `false` 只搜索 dir 顶层；`true` 搜索其子目录，仍不跟随链接 |
| `sha256` | 可选，无限制 | 额外旧文件哈希条件；省略即可仅按名称删除，不允许空字符串 |

Windows 文件名匹配不区分大小写。命中的全部普通文件都处理，多规则命中同一路径时去重。目录不存在或没有命中视为成功；不删除目录本身。首版只有 exact/contains，不解释通配符或正则。

- 只删除同名文件：`{"dir":"mods","match":"exact","name":"ExampleMod.jar"}`。
- 删除文件名包含字符串的文件：`{"dir":"mods","match":"contains","name":"ExampleMod"}`。
- 递归清理：增加 `"recursive": true`。
- 同名且哈希吻合才删除：再增加 `sha256`。条件是 AND；哈希不符的文件跳过并记录，不扩大到其他文件。

删除候选先扫描并固化，下载期间不修改现用文件；提交前复查候选未被外部修改，变化则重新检查，不盲删。删除以移入事务备份实现，失败可恢复。

**防止新旧模组同名片段互相冲突：当前清单声明的所有单文件目标和 ZIP 展开的所有目标优先保留。** 即使删除规则命中，也从删除集合排除；包括本轮无需下载的文件和 seed 文件。比如 contains=ExampleMod 可以清理旧版，同时 files 中的 ExampleMod-2.0.jar 始终保留。排除记录到日志；若确实要删除某文件，先移除它的 files/archives 声明。

### 3.4 压缩包 `archives[]`

| 字段 | 必填 / 默认值 | 说明 |
| --- | --- | --- |
| `path` | 必填 | 解压目标目录，相对游戏目录；`.` 表示游戏目录根 |
| `sha256` | 必填 | ZIP 文件本身的 SHA-256；换包后更新此值，无需额外版本号 |
| `url` | 必填 | ZIP 的 HTTPS 下载地址 |
| `source` | 可选，`""` | 包内要提取的目录；空字符串使用包根。填 `client/` 表示剥掉此前缀，只取其内部内容 |
| `policy` | 可选，`managed` | 与 files 相同，逐个解压后的文件应用；`seed` 不覆盖已经存在的文件 |

只支持 ZIP，不增加格式字段，不从扩展名推断其他格式。source 必须是包内相对目录，不支持模糊匹配；指定目录不存在或其中没有普通文件时报错。

例如包内容为：

```text
client/
  config/example.cfg
  scripts/fix.zs
```

- `source="client/"`、`path="."` → `config/example.cfg` 和 `scripts/fix.zs`。
- `source="client/config/"`、`path="config"` → `config/example.cfg`。
- 包根直接是 config/scripts 时，`source=""`、`path="."` 即可。

path 为 `.` 仅表示映射基准，不允许覆盖存档或其他受保护位置；每个展开后的目标仍逐个验证。解压为覆盖合并，不清空目标目录。新版 ZIP 不再包含的旧文件不会自动删除，需要用 remove 明确清理。

## 4. 压缩包更新与文件管理

ZIP 是同一文件事务的输入方式，属于本次功能范围，不能仅留作以后扩展。

1. 下载 ZIP 到暂存区，验证包 SHA-256 后再读取内容。
2. 校验包内条目并按 source/path 映射目标，检查路径越界、链接、重复路径、文件/目录冲突和展开体积上限。损坏、加密或不支持的 ZIP 返回明确错误。
3. 解压到独立暂存目录，在后台计算每个展开文件的 SHA-256，得到本地文件索引。索引绑定接口地址、包 SHA-256、source、path、policy；接口不必再列出包内的每个文件。
4. 将 ZIP 文件索引和 files 合并成完整目标集合，再生成最终删除集合。两个 ZIP 或 ZIP 与 files 声明同一文件路径时直接报清单冲突，不靠数组顺序覆盖；目录共享允许，文件目标重复不允许。
5. 根据 managed/seed 计算真正需要安装的文件，与普通文件一起备份、提交、回滚。包处理记录仅在整批事务成功后保存。
6. 同一个 ZIP 的 SHA-256 没变时，仍根据本地索引检查展开文件。managed 文件缺失或内容变化则修复；seed 只补缺失。不能仅凭“以前解压过”就跳过。
7. 保留经过验证的 ZIP 缓存供修复；使用缓存解压前重新验证包哈希。缓存丢失时按需重新下载。本地索引丢失或格式损坏时，从验证后的 ZIP 重建。手动完整修复重建索引并重算文件哈希。
8. ZIP 内容或 source/path/policy 改变时，重建对应索引。改变目标位置不会自动清理旧位置，仍使用 remove。

本地索引是工作状态，不是防本地恶意篡改的认证机制。初次绑定已有完整客户端、又没有索引和 ZIP 缓存时，需要下载一次包建立索引；这是保持 API 简单的代价。

files 和 archives 应保留当前仍需要维护的全部文件/包，不能只发布最近一次增量。跨版本客户端可能跳过多个发布，历史删除规则应保留到相关旧版不再支持。移除清单中的文件/包只表示停止维护，不等于删除本地文件。

客户端对规范化清单计算摘要，避免重复展示相同说明；摘要不能用于跳过文件和删除规则检查。对同一批次的重复操作应得到同一结果，重复启动不会反复下载正常文件。

## 5. 运行流程与失败策略

```text
实例绑定与任务互斥检查
→ 恢复未完成事务
→ 获取、严格验证清单
→ 获取或重建 ZIP 索引，校验所有目标路径与冲突
→ 后台计算文件差异，生成下载计划与删除候选
→ 无差异则结束
→ 按 silent 决定自动执行或整批确认，显示任务进度
→ 下载所需文件与 ZIP，校验 SHA-256，暂存解压内容
→ 合并最终安装计划，删除候选排除全部保留目标
→ 检查空间、文件占用及计划中的旧文件是否发生变化
→ 写恢复日志，备份旧文件
→ 安装新文件、移走明确删除的旧文件
→ 核验最终受管理文件，原子提交成功状态
→ 继续现有游戏启动步骤
```

- 默认客户端更新不可跳过：联网检查失败、校验失败、取消更新均终止本次游戏启动，提供重试；启动器本身仍可使用。公告获取失败不阻塞游戏。离线模式也不默认绕过更新；未来若需要离线游玩，另行明确本地策略。
- 下载阶段允许取消且不修改现用文件；提交阶段禁止即时取消，先完成或恢复到一致状态。
- 使用实例目录内 `.nutmod-update/` 保存 staging、backup、journal、state；暂存与目标需在同卷。若 gameRoot 为外部链接目录，首版拒绝绑定，不能假定同卷。
- 状态按实例保存，并包含接口地址、清单摘要和事务标识；成功状态不能早于文件落盘。成功备份保留最近一次，未完成事务的备份不能自动清理。
- 多文件安装不是一次原子操作：逐项写入可恢复日志、用同卷重命名移动文件，记录每项提交进度。异常退出后在下次启动恢复，恢复不成功时保持禁止启动并保留备份。需处理状态提交前后崩溃的幂等恢复。
- 使用实例级跨进程锁保护检查到提交；手动更新拒绝游戏正在运行的实例。启动链中的 `LaunchTask::create()` 已经调用 `setRunning(true)`，任务不能仅看到 `isRunning()` 就拒绝自己，必须区分自己持有的启动流程与另一个运行实例。
- 开机后台检查只读；手动更新、启动更新、实例编辑和启动器自更新需要协调，避免安装期间启动、修改模组或退出进行自更新。
- 哈希与磁盘操作在后台执行，复用现有任务信号向 UI 报告进度。不要在 UI 线程扫描大型模组。

### 5.1 更新期间禁止启动游戏

这是客户端固定行为，不增加 API 开关，silent=true 时同样生效。

- 当前启动器有客户端更新操作执行时，拦截所有新的游戏启动请求。覆盖下载、校验、ZIP 解压、备份、替换、删除、最终提交和回滚阶段，不能只在覆盖文件的瞬间禁用启动。
- 进入更新流程前原子获取操作权限，然后再启动下载；操作完全结束后才释放。后台只读查询清单不需要阻止启动，但从查询转入下载/应用必须先获取权限。为了建立 ZIP 索引而进行的下载也属于更新流程。
- 主界面持续显示“客户端正在更新，请在更新完成后再启动游戏”。启动按钮显示“更新中…”并禁用，提示文字放在状态区，不能仅依赖禁用按钮的点击或悬停事件。
- 双击实例、快捷键、菜单、命令行或其他启动入口同样在后端被拦截；有界面时显示上述提示，无界面时输出明确错误。重复请求合并提示，不堆叠对话框，也不排队多个启动请求。
- 用户最初点击启动所触发的启动前更新，是更新任务的所属启动流程：它等待更新成功后继续，不能把自己误判为另一个启动请求。更新成功到游戏启动之间保留所属启动流程的操作权限，避免刚解锁又被手动更新插入。
- 手动更新结束后恢复启动按钮，不自动启动游戏。下载失败或取消后，待下载器确实停止、清理或回滚完成才解除“更新中”；本次启动已经取消，下次点击需重新通过更新检查。若恢复失败，显示“客户端更新未完成，请先重试修复后再启动游戏”，保持启动门禁并允许修复任务进入。
- 反向同样互斥：目标实例正在准备启动或游戏进程仍在运行时，不开始其客户端更新，提示“请先关闭游戏，再更新客户端”。不能只依赖 UI 状态；用所属操作令牌区分启动链自己的更新和外部更新。
- 进程内使用统一的更新/启动协调状态；跨进程按规范化实例路径与游戏目录保护同一资源。两个启动器进程不能一个更新同一实例、另一个启动它。不可用“先判断布尔值，再启动”的分离操作代替互斥获取。
- 应用重启后，检查未完成事务日志再允许启动；内存中的 updating 标志消失不代表上次更新成功。

验收需在下载、解压、替换、删除、回滚每个阶段尝试所有启动入口；验证静默更新也被拦截、重复点击不重复启动、失败后可重试、恢复失败不放行，以及同一实例双进程互斥。

## 6. 必须约束的文件操作

- 拒绝绝对路径、盘符、UNC、`..`、NTFS ADS、设备名、尾随点/空格；对大小写不敏感的重复路径、父子路径冲突报错；files/archives 的目标重复报错，remove 命中这些目标时按保留优先规则排除。
- 验证目标及已有父目录，不穿过 symlink、junction 或其他重解析点；计划生成和提交前都验证。仅字符串前缀比较不足以保证目录边界。
- 首版写入范围限制为实际需要的 `mods/`、`config/`、`scripts/`、`resourcepacks/` 等明确目录。存档、账号、启动器程序、实例配置、`mmc-pack.json`、patches、库与 Java 运行时不属于该更新器范围。
- 客户端设置清单体积、条目数、单文件和总下载大小上限，按实际接收字节计数，不依赖 API 的 size 字段；限制超时和重试。严格检查 HTTP 结果、重定向最终协议和哈希，防止把错误页面作为文件安装。
- 清单和文件使用 HTTPS；当前文件的 HTTP 入口建议替换。下载 URL 的签名查询参数不写入用户可见日志；复用下载器时检查它现有的 URL 日志输出。
- ZIP 必须先校验包哈希、解压到暂存区，检查路径、链接、大小和条目上限，再将文件纳入同一事务；不能只记录“压缩包版本已处理”而不检查文件结果。

## 8. 实施顺序与验收

1. 发布端：增加生成清单脚本，从指定受管理文件计算 SHA-256；检查重复路径和缺失 URL；先上传文件并验证公开下载内容，最后发布清单，不能先发布指向未上传文件的清单。
2. 实现新协议解析、实例绑定、managed/seed、exact/contains 删除、ZIP 索引与解压、下载校验、事务恢复及启动门禁；先用 OpenBlocks.cfg 验证基础流程，再联调 ZIP 与删除。
3. 完善手动更新/修复入口、打包绑定、状态提示和日志。配置覆盖在界面明确说明并提示备份位置。
4. 完成单文件、ZIP 和删除规则的混合事务验收；后续再按实际需求扩展签名清单和性能优化。

验收覆盖：首次更新、无变更、同版文件损坏、seed 保留修改、模组改名、删除哈希不符跳过、exact/contains 大小写匹配、递归开关、模糊删除保留新版文件、跨版本更新、其他实例不受影响；404/断网/错哈希/磁盘满/占用/取消；提交每个阶段中断后恢复；重复点击与双进程；路径越界、链接目录及大小写冲突。另测 ZIP 首次安装、同包修复、seed、source 映射、索引/缓存丢失、多个包重名、坏包、路径穿越和解压超限。用隔离的测试实例，不能拿玩家唯一存档做故障注入。
